## Rules

1. Create one entry per distinct topic in the capture. Entry types:
   - "discussion": a conversation with someone (1:1, hallway, chat thread)
   - "meeting": a scheduled meeting that happened or is being summarized
   - "task": work {user_name} or a teammate needs to do, tracked informally
   - "note": anything worth remembering that isn't the above
   - "status_update": progress {user_name} wants to log (often ClickUp-bound)
2. PERSPECTIVE: the capture is always written by {user_name}. Frame entries from
   their point of view — {user_name} is the implicit actor. When {user_name}
   reviewed, discussed, attended, or unblocked something, that work is THEIRS even
   if other people are named. Do NOT put {user_name} in "people"; "people" is for
   OTHERS mentioned (teammates, stakeholders). First names are fine; match known
   people when obvious.
3. ACTIVITY TAGS: always include a tag describing what {user_name} did, so their
   activity is queryable. Use a consistent vocabulary, lowercase:
   - "review" — reviewing an MR, design, doc, or someone's work
   - "discussion" — a conversation/sync (pairs with type "discussion")
   - "meeting" — a meeting (pairs with type "meeting")
   - "follow-up" — chasing or continuing prior work
   - "decision" — a decision was made
   - "blocker" — something is blocked or blocking
   Then add up to 2 topical tags (project/area, e.g. "video", "partner"). Reuse known
   tags when they fit; invent at most one NEW topical tag per capture.
4. Titles are short (under 80 chars), specific, past-tense for things that happened.
5. FOLLOW-UPS: if the capture continues, updates, or chases an item already in the
   "Recent entries" list above, set "follows_up_entry_id" to that entry's number
   (the #N). It will be threaded under the original. Only set it when you are
   confident it is the same thread of work; otherwise leave it null. Never invent an
   id that is not in the list.
6. Reminders: only when there is a follow-up, deadline, or "by <date>" commitment.
   Resolve relative dates ("Friday", "tomorrow", "next week", "EOD") to an ISO 8601
   datetime relative to today. Default to 10:00 local time when no time is given;
   use 18:00 for "EOD". A bare weekday means the NEXT occurrence of that weekday.
7. EXISTING-WORK CHECK (do this BEFORE drafting a task): if the capture is clearly
   about work that already has an open Watson card in the list above, set
   "existing_work_clickup_id" to that card's related_clickup_id. Watson will route
   the MR (if any) onto the existing card instead of creating a duplicate task — so
   you do NOT need to draft a clickup_create_task in that case. Signals that point
   to an existing card:
   - The capture references an MR whose branch/title clearly belongs to the SAME
     parent ClickUp task already on a card (cross-repo, same requirement).
   - The capture references the SAME ClickUp task id, MR id, or topic as an existing
     card (note vs. follow-up vs. additional MR on the same work).
   ONLY set "existing_work_clickup_id" when you are confident — if uncertain, leave
   it null and draft a normal create_task. Never invent ids that aren't in the list.

8. clickup_actions: draft exactly one "clickup_create_task" — a NEW task assigned to
   {user_name} in their own list. This task is a LOG OF WHERE {user_name}'S TIME
   WENT, not a tracker of other people. NEVER comment on, reassign, or restatus a
   task owned by someone else. The "draft" MUST be an object:
   {"name": "...", "description": "...", "labels": ["..."]}.
   - category: how the time was spent — pick exactly ONE of these TWO only:
       "Review"     — code review, MR review, design review, doc review.
       "Discussion" — everything else: 1:1, sync, meeting, status update,
                      follow-up, decision, debugging-with-someone, anything
                      that's a conversation or summary of {user_name}'s own work.
     When in doubt, choose Discussion. NEVER emit any other category string —
     no "Meeting", "Work", "Status", "Note", etc.
   - name: "<Category> - <work/topic>" — START with the category prefix (always
     exactly "Review" or "Discussion"), then a plain noun phrase naming the
     subject and the people involved. The prefix lets {user_name} scan the
     month-end list by bucket. {user_name} is a PARTICIPANT/DOER, not a
     supervisor.
       GOOD: "Discussion - Playback button unclickable bug (Calendar app) with Jordan"
       GOOD: "Review - Morgan's iframe z-index fix"
       GOOD: "Discussion - Video module bottom-docked ad scaling with Bob"
       BAD — NEVER write the name this way: "Track Jordan's investigation",
       "Follow up on X", "Monitor Y". No track/monitor/follow-up/oversee framing —
       name the WORK itself, not the act of watching it.
     When the capture references an MR (by number like `!6315`, by project name,
     by URL, or by branch substring), or a ClickUp task (by id or partial name),
     LOOK IT UP in the lists above and use the ACTUAL TITLE in the task name.
     Never use bare numbers/ids in the name — those aren't human-readable.
       BAD:  "Review - frontend-service MR !6315"
       GOOD: "Review - <actual MR title from the GitLab MRs list>"
   - labels: the chosen category (e.g. "Discussion"), optionally plus ONE topical
     area (e.g. "video module","video"). 1-2 labels total.
   - description: brief detail. If it relates to an existing task in the list above,
     add a "Related to: <task name> (<id>)" line (context only — that task is never
     modified) and set "suggested_task_id" to its id so the new task can link to it.
     If it relates to an MR in the GitLab MRs list, set "suggested_mr_id" to that
     MR's id (format "<project_id>!<iid>") AND add an "MR: <title>" line to the
     description. Only use ids that appear in those lists — never invent them.
   Only emit an action when {user_name} actually invested time in something worth
   logging. NEVER invent task ids; set "suggested_task_id" to null if nothing matches.
9. If the capture is trivial or empty, return empty arrays. Do not pad.

      "existing_work_clickup_id": "null OR a related_clickup_id from the Open Watson cards list when this capture is about work already on a card",

NOTE: "type" must be one of discussion | meeting | task | note | status_update.
(Use the "review" activity via TAGS, not as a type — a code review is a
"discussion" or "note" with the "review" tag.)

"follows_up_entry_id" is the #N of an existing entry from the Recent entries list,
or null.

Always use "kind": "clickup_create_task". The new task is created in {user_name}'s
own list and assigned to them automatically — do NOT use clickup_comment or
clickup_status (Watson must never modify other people's tasks).

9. gcal_events: draft a Google Calendar event ONLY when the capture explicitly
   asks to schedule / book / send a calendar invite / block time / create a
   meeting. Signals: "schedule", "book a call", "send calendar invite",
   "create a meet link", "block time for", "put on my calendar".
   Do NOT draft a gcal_event just because a reminder mentions a time — a
   reminder like "remind me to check with Bob at 7pm" is JUST a reminder,
   not a calendar event. The user must have asked for a calendar action.
   Fields:
   - "title": short human summary, e.g. "Check-in with Bob on Playback updates"
   - "start_at": ISO 8601 with local TZ offset (e.g. "2026-07-15T19:00:00+05:30")
                 — resolve relative phrases ("7 PM today", "tomorrow 3pm") to
                 absolute ISO strings using today's date {today}.
   - "end_at":   optional ISO. If omitted, Watson defaults to start + 30 min.
   - "duration_minutes": integer, used only when end_at is missing (default 30)
   - "attendees": list of email addresses for the people named in the capture.
                  For each name, look them up in the "Known contacts" section
                  above and use that email. If the name doesn't appear there
                  and no email is in the capture text itself, LEAVE THE ENTRY
                  OUT — never invent or guess an email address. Empty list is
                  fine when no attendee is known.
   - "description": optional context for the invite body
   - "add_meet": true unless the capture says "no meet" / "in person" / "phone"
   Example output block, for a capture like "create a meet link and calendar
   invite for check-in with Bob on Playback at 7 PM today":
      "gcal_events": [
        {
          "title": "Check-in with Bob on Playback updates",
          "start_at": "2026-07-15T19:00:00+05:30",
          "end_at": "2026-07-15T19:30:00+05:30",
          "duration_minutes": 30,
          "attendees": [],
          "description": "Sync on Playback progress.",
          "add_meet": true
        }
      ]
   When no calendar action is asked for, return an empty list.
